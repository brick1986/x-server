## 1. 锁模型（泛化）

修订原 §4.2 的 `lock:player:{id}`。

### 1.1 锁粒度：按实体，不按玩家

泛化为 `lock:{entity}:{id}`：

- `lock:player:{id}` —— 玩家私有数据（profile / bag / equipment），一个玩家一把。同玩家大多只操作自己数据，天然低竞争。
- `lock:guild:{id}` —— 公共实体（工会等），按公共实体 ID 分锁，竞争真正发生在这里。
- 后续新增实体（拍卖行、帮派战等）按同一规则 `lock:{entity}:{id}` 分配。

### 1.2 锁类型：统一互斥 `RLock`

读写都用同一把 `RLock`，不引入 `RReadWriteLock`。理由：同玩家锁天然低竞争，读吞吐代价可接受；互斥一把锁走天下，推理最简单。这也使"读路径回填用普通 `SET`"成立——持锁期间无并发写，无需 `SET NX`。

### 1.3 跨实体加锁：全局类型优先级

一个操作同时触玩家数据 + 公共数据（如玩家向工会捐献：扣玩家货币 + 改工会数据）时，按实体类型的**全局固定优先级**依次加锁，防死锁。菜鸟期优先级表：

```
guild > player   （先加 guild 锁，再加 player 锁）
```

新增实体类型时，在此表登记其优先级位置。**同类型内**（如两个玩家转账）沿用原方案按 ID 序加锁（`lock:player:{min}` + `lock:player:{max}`）。

## 2. 读写路径正确性流程

修订原 §4.1 读路径与 §4.2 写路径，消除回填丢更新竞态（#2）。

### 2.1 读路径（持锁）

```
acquire lock:{entity}:{id}        # 同实体，读写共用
  v = GET key                      # Redis
  if v == nil:                     # miss
    v = LOAD Mongo(key)            # 锁内从 Mongo 加载
    SET key v                      # 回填，普通 SET（持锁，无并发写，安全）
  release lock:{entity}:{id}
return v
```

关键点：回填是**普通 `SET` 不是 `SET NX`**——持锁期间不可能有并发写，`SET NX` 的防覆盖语义用不上。回填全程在锁内，消除原竞态（原竞态根因是回填不持锁，会把持锁写的 v2 覆盖回从 Mongo 读到的 v1）。

### 2.2 写路径（持锁，含 miss 加载）

```
acquire lock:{entity}:{id}
  v = GET key
  if v == nil:
    v = LOAD Mongo(key)             # 写路径也要在锁内处理 miss
  v2 = modify(v)                    # Java 侧读-改
  if not isHeldByCurrentThread():   # 提交门控，见 §4
    throw LockLostException         # 不持锁绝不写
  Lua: SET key v2; SADD dirty key   # 唯一提交点
release lock:{entity}:{id}
```

关键点：原 spec 写路径隐含"key 一定在 Redis"，但冷 key 首次写会 miss。现明确**写路径 miss 也在锁内从 Mongo 加载**，与读路径同源，保证读-改建立在真实数据上。

### 2.3 跨玩家/跨实体写

沿用原 §4.2 第 3 点"按 ID 序加双锁 / 按全局类型优先级加锁"，持锁期间完成各实体的独立覆盖写，顺序仍是**先写业务日志 → 覆盖写 A → 覆盖写 B**。每个实体的覆盖写各自走 §2.2 流程（含提交门控）。

### 2.4 回填与落盘的交互

落盘进程扫 dirty 时 `GET key` 读到的永远是"某次持锁写完成后的整值"——因为回填是持锁普通 `SET`、写是持锁 Lua `SET`，Redis 里该 key 的任意瞬间态都是某个完整 v2，不会出现半截/中间态。落盘 `upsert` Mongo 的安全性不变。

## 3. 并发池配比

修订原 §3.1"载体线程池与连接池比例约束"，删除错误规则（#1）。

### 3.1 删除的错误规则

原 §3.1：

> 载体线程池大小（`jdk.virtualThreadScheduler.maxPoolSize`）应 ≥ 各数据库连接池上限之和……避免连接池耗尽时虚拟线程批量阻塞。

删除。理由：虚拟线程等连接时 park 释放载体，不占载体线程，"批量阻塞"在此良性；把载体池开到比连接池总和还大反而允许更多并发去抢连接，放大耗尽风险。这条诊断错、方向反。

### 3.2 新规则：禁嵌套获取

代码纪律：一个虚拟线程**绝不同时持有两个连接池的连接**。用完一个池的连接、归还后，再去取另一个池的。

- 落盘进程：扫 dirty → `GET` Redis（取/还 Redis 连接）→ `bulkWrite` Mongo（取/还 Mongo 连接），两步分离，不嵌套。
- 业务读写路径：`GET` Redis（还）→ 若 miss `LOAD` Mongo（还）→ `SET` Redis（还），每步独立借还，天然不嵌套。

### 3.3 新规则：按需定池

每个连接池大小按**该池自身的峰值并发需求**定，不再与载体池绑定：

- Redis 连接池 100~200：覆盖业务读写并发请求数。
- Mongo 连接池 50~100：覆盖落盘 bulkWrite + 冷启动加载并发数。

载体线程池用 JDK 25 默认（基于 CPU 核数），**不再通过 `maxPoolSize` 强行放大**。

### 3.4 安全性论证

死锁唯一形态是"嵌套跨池获取"（持 A 等 B）。禁嵌套后，任一时刻一个虚拟线程最多持一个池的连接，池间无循环依赖 → 无死锁。连接池耗尽时等待方 park 等 release，不传播死锁，最终都能拿到；并发超过池大小则按池大小自然限流，而非崩溃。

## 4. 看门狗去除 + 提交门控

修订原 §3.1"看门狗续约上界"与 §8 对应待定项，消除 #3。

### 4.1 锁租约：固定 `leaseTime`，无看门狗

加锁一律传 `leaseTime`、禁用看门狗（不使用 Redisson 默认无限续约）：

```
lock.lock(10, TimeUnit.SECONDS)   # 固定租约 10s，不续约
```

- 10s = 正常覆盖写（<100ms）的 100 倍裕度。
- 操作正常完成 → 主动 `unlock`，锁立即释放。
- 操作超过 10s → 锁 TTL 自然到期释放，**无锁毒**：进程卡死但活着，锁最迟 10s 自愈；进程硬崩，锁随租约释放（与原方案硬崩场景无差异）。

### 4.2 提交门控：不持锁绝不写

覆盖写唯一提交点是 `SET + SADD` Lua。执行 Lua 前强制校验：

```
if not lock.isHeldByCurrentThread():
    throw LockLostException        # 锁已失效，放弃本次写
# 否则执行提交 Lua
```

- 正常路径：isHeld 为 true，提交正常。
- 租约到期（操作超 10s）：isHeld 为 false，抛异常，客户端重试。fail-fast，绝不带着失效锁完成写。
- 把原"看门狗停止续约 → 静默破串行"的危险语义，换成"租约到期 → 显式 abort"。

### 4.3 TOCTOU 残窗与升级路径

`isHeld` 检查到 Lua 执行之间有微窗口：仅当操作恰在租约边界（已跑 ~10s）且锁在这几微秒内过期、且另一实例恰在此刻拿到锁并发写，才会漏。菜鸟期接受。

**升级路径（成熟期，菜鸟期不落地）**：若日后证明该残窗真出事，把提交 Lua 改为 token 门控——锁 token 作参数传入，Lua 内原子校验"锁 Hash field 当前值 == 传入 token"后才 `SET+SADD`，彻底消除窗口。代价是 Lua 与 Redisson 锁内部 Hash 表示耦合，届时再评估。

注：Redisson 锁自身的获取/释放已是 token 门控（基于 `clientId:threadId` Hash field），但那保护的是**锁 key 的互斥与重入**，不覆盖我们的**数据 key 提交**。数据提交的"是否还持锁"门控需自行实现，本节即其菜鸟期实现。

### 4.4 对原 spec 的具体删改

- 删原 §3.1"必须自定义看门狗的最大持有时长/最大续约次数，超限停止续约让 TTL 自然释放"整段。
- 原 §3.1"同玩家写串行化"段补：加锁固定 `leaseTime=10s`、禁用看门狗，提交前 `isHeldByCurrentThread()` 校验，失锁即 abort。
- 原 §8"Redisson 分布式锁看门狗上界方案"待定项删除（已定，不再待定）。
